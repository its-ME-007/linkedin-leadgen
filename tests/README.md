# Tests

This folder contains the test scripts and generated outputs used to validate the LinkedIn Lead Engine pipeline.

The tests currently work as integration-style tests rather than isolated unit tests. They exercise the actual services and external providers used by the application.

## Folder Structure

    tests/
    │
    ├── README.md
    │
    ├── test_discovery.py
    ├── test_signal_extractor.py
    ├── gemini_model.py
    │
    └── output/
        ├── discovery_results.json
        └── extracted_signals.json

---

## 1. Discovery Test

### File

    tests/test_discovery.py

### Purpose

Tests the DiscoveryService using the LinkedIn MCP provider and the configured web-search service.

The test:

1. Connects to the LinkedIn MCP server.
2. Defines discovery criteria.
3. Generates queries using the signal grammar.
4. Searches LinkedIn for every generated query.
5. Searches the web for every generated query.
6. Normalizes the returned results.
7. Deduplicates the results.
8. Saves the discovery output.

### Example Criteria

    criteria = {
        "location": "Bangalore",
        "signal_types": [
            "office_expansion"
        ],
        "industry": "technology"
    }

### Run

From the project root:

    python -m tests.test_discovery

### Output

The test writes:

    tests/output/discovery_results.json

This file contains the discovery results that are passed to the signal extraction stage.

## 2. Signal Extraction Test

### File

    tests/test_signal_extractor.py

### Purpose

Tests the SignalExtractor using the discovery output generated by the discovery test.

The extractor:

1. Loads discovery_results.json.
2. Filters discovery results into candidate signals.
3. Sends candidate content to the configured Gemini model.
4. Extracts structured business signals.
5. Determines signal intent and confidence.
6. Determines whether the signal is qualified.
7. Preserves source and discovery-query information.
8. Writes the extracted signals to disk.

### Run

    python -m tests.test_signal_extractor

### Input

    tests/output/discovery_results.json

### Output

    tests/output/extracted_signals.json

---

## 3. Gemini Model Test

### File

    tests/gemini_model.py

### Purpose

Lists the Gemini models available to the configured Google Gemini API key.

This is useful for checking:

- Whether the API key is valid.
- Which models are available.
- Which models support generateContent.
- Which model name should be used by SignalExtractor.

### Run

    python -m tests.gemini_model

The output lists the available models and their supported actions.

## Test Pipeline

The main tests are intended to be run in this order:

    Discovery
        |
        v
    tests/test_discovery.py
        |
        v
    discovery_results.json
        |
        v
    Signal Extraction
        |
        v
    tests/test_signal_extractor.py
        |
        v
    extracted_signals.json

The Gemini model test is independent and is primarily used to verify model availability.

## Generated Output Files

### discovery_results.json

Contains the results returned by the discovery stage.

The results retain information such as:

- Source
- Signal type
- Discovery query
- Raw result

Example structure:

    {
        "criteria": {
            "location": "Bangalore",
            "signal_types": [
                "office_expansion"
            ],
            "industry": "technology"
        },
        "result_count": 20,
        "results": []
    }

The exact contents depend on the providers and searches executed during the test.

---

### extracted_signals.json

Contains the structured signals produced by the signal extraction stage.

Example structure:

    {
        "input_result_count": 20,
        "retained_signal_count": 7,
        "qualified_signal_count": 7,
        "needs_enrichment_count": 0,
        "signals": [
            {
                "signal_type": "office_expansion",
                "company_name": "Example Company",
                "location": "Bangalore",
                "intent": "planned",
                "recency": null,
                "confidence": 0.9,
                "status": "qualified",
                "evidence": {
                    "text": "Example evidence",
                    "reason": "Example reason"
                },
                "source": "linkedin",
                "source_url": null,
                "discovery_query": "\"new office\" \"Bangalore\" \"technology\""
            }
        ]
    }

## Environment Variables

The tests require the appropriate API credentials to be available through environment variables.

For Gemini:

    GEMINI_API_KEY

For example, in PowerShell:

    $env:GEMINI_API_KEY="your-api-key"

Verify that it is available:

    echo $env:GEMINI_API_KEY

Do not commit API keys to the repository.

## External Services

These tests depend on external services.

The discovery test currently depends on:

- LinkedIn MCP
- Web search provider

The signal extraction test depends on:

- Google Gemini API

Therefore, failures can occur because of:

- API rate limits
- Invalid API keys
- Model availability
- Network errors
- MCP connection errors
- Provider-side errors

These failures do not necessarily indicate a problem with the application logic.

## Current Testing Philosophy

The tests currently validate the pipeline progressively.

    1. Can we discover relevant content?
                    |
                    v
    2. Can we preserve the source information?
                    |
                    v
    3. Can we identify actual business signals?
                    |
                    v
    4. Can we structure those signals consistently?
                    |
                    v
    5. Can we identify qualified opportunities?

The goal is to keep each stage observable before connecting it to the next stage of the lead-generation pipeline.
